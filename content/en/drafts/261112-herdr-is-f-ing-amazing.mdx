## The thing I wanted

I want several agents running at once. One handles the main task, another checks its work, maybe a third researches a detail. They need to hand work to each other. I need to see what they are doing. 

That last part rules out a lot of the obvious orchestration advice. Start agents in the background, wait for a result, and inspect the output later? No. The sub-agent disappears into a process. I cannot watch what it does, and I will not run work I cannot see. {Mention built-in subagents in most harnesses, they can be switched to view. Most providers only allow 1 account per person, I dont want to subscribe to the highest tier, some with the highest tier still hit limit, so you cheat, or use multiple providers/harnesses. I know about T3Code, it's a cool project, you use multiple harnesses in one app. I like that idea, but I dont really like moving to a very opinionated app, it currently doesnt support plugins/mods (verify)so it's a little hard to fit my existing workflow. (check notes about T3Code)}

Putting every terminal on screen solves visibility and creates a different problem. Every worker costs screen space, including the four I am not reading, and the arrangement only exists inside that one window. I wanted a place for the agents, not a permanent wall of terminals.

## Core made the terminals addressable

The change came when I moved the team to [`herdr-core`](https://github.com/herdrdev/herdr-core "mention | Headless server that runs named persistent terminals for the desktop and phone clients"). Core runs terminals without drawing a UI. I can start one, address it by name from the `hc` CLI, send it work, wait, and read the result. The program exists without taking up a pane on my screen. {I moved from herdr tui to herdr app, core is the underlying thing. I read a blog post about the new app, it looks cool. It has the vertical tabs that I liked (I was using cmux for the exact reason), so I checked it out. In their homepages there are some screenshots, I saw in some of them agents status, that was cool, I digged in, I loved it.}

The status is not a guess from a screenshot. A reporting program sends its state through OSC 7501, the Program Status Protocol. In shell form, a program can report blocked like this:

```bash
printf '\e]7501;state=blocked:app=my-agent\e\\'
```

Core does not scrape terminal text or recognize agent brands. It knows what the program reports. If a program does not report, it has no agent status; `hc wait` can only wait for it to exit. That boundary matters. A badge is useful because the program says what it is doing, not because a UI guessed from one frame of output.

The team has a shape now: space for a project, tab for a task, panes for agents. The lead's sub-agents appear under it. That last part is not cosmetic. I can see which worker belongs to which lead instead of keeping a second list in my head.

My first real core team was small: an omp pane answered `READY`, `hc wait` returned `done` at turn 1, and I removed the pane. Boring. Exactly the kind of result I wanted from the plumbing.

## The desktop is where I work

[`herdr-app`](https://github.com/herdrdev/herdr-app "mention | Desktop client that arranges core terminals into spaces, tabs, and panes") puts those running terminals into a desktop workspace. I organize by project, put tasks in tabs, and keep agents in panes. The sub-agents sit under the lead that started them {I dont need to see the sub-agents panes all the time, but they're still accessible with just one click}. 

When I want to check one terminal, I can peek at it without reshuffling the whole window. `terminal.peek` gives me a temporary look; `terminal.show` places it in a pane. I used to think visibility meant a pane for every worker, permanently arranged. Now the terminals keep working while I decide which one to open.

There are rough edges. `layout.apply` is destructive: it can kill and recreate shells, so I do not treat it as a harmless way to resize a grid. There is no `pane.rename` command and no documented one-shot tiling verb, which is why I still have my own `hgrid.py`. I also have not found a documented operation to move a live terminal directly between tabs. I would rather keep my layout scripts than pretend those gaps are solved.

Core does not bring a lost agent's task back after the server or machine restarts. A kept terminal can return as a shell in its old directory; that is not the same thing as resuming the work. App mods are another boundary: they are trusted JavaScript with network access and unrestricted commands. I would not install one casually.

## The same herd on my phone

The phone is where this setup makes sense away from the desk. The [`Herdr` phone app](https://herdr.dev/mobile/ "reference | Official mobile client connects to herdr-core over SSH") connects to core over SSH. It does not need a Herdr account or a vendor relay. It shows the same agents in an Inbox sorted `needs you`, `done`, `working`, and `idle`, then opens the live terminal so I can read it and type into it. Looking at a terminal does not resize the desktop panes.

I spent time in April researching this exact problem: Blink, Moshi, Mosh, tmux, the whole phone-to-host chain. I wrote down a Moshi + Mosh + tmux stack that looked like it should work. I prepared the host, then never set the push token, so notifications never worked. I kept wanting remote access to mean I could see and act on the same work, not squint at a terminal session that might have lost its connection.

Now I open the phone and see the herd. The app is six days old as I write this, so this is not a claim that every setup is frictionless. It needs `herdr-core` running and SSH reachability; away from home that means SSH over Tailscale. The iOS app is version 1.0.5. There are open reports from Android users about key authentication and from a user asking for ProxyJump support. Those are reports, not proof that everyone hits the same bugs. The phone app also does not offer a separate approval card or let me edit the desktop layout. When an agent needs me, I can open its terminal and respond there.

The TUI has its own phone route through any SSH client, but that is not this app. The phone app connects to core; TUI sessions are separate and never appear in its Inbox. Moving the team to core is what made the phone part possible.

## New on top of old things

The app is six days old. Everything it stands on is older.

Terminal emulation is Ghostty's. `herdr-app` builds a local `ghostty-sys` crate whose manifest reads "Generated bindings to upstream libghostty-vt (vendor/ghostty)". The TUI carries `ghostty-vt`, described in-tree as "Herdr's binding to its vendored libghostty-vt", and core depends on the same crate. The VT engine I already trusted, in a different frame.

The agents are ordinary programs. Core owns a pseudo-terminal per terminal and starts children through `spawn_pty`; `hc run` takes any command, `hc send` types into it, `hc read` gives back the screen and the scrollback. Nothing about omp or Hermes changed to run here. My team script is a few hundred lines calling the same CLI any shell could call.

The desktop UI is not theirs either: `herdr-app` vendors GPUI, the framework from Zed, with its Apache licence sitting in the tree next to the vendored Ghostty. New composition over old parts.

What I did give up, so the sentence stays honest: an agent must run inside a core terminal before the app or the phone can see it. A program that does not report has no status at all, and `hc wait` falls back to waiting for the process to exit. And a restart returns a pane as a fresh shell, not the work that was in it. Those are boundaries of the layer I chose, not of the terminal underneath.

## It is a place, not a vendor bet

The protocol is the part I care about beyond one app. OSC 7501 is open. A program that reports its state can show up in the same list, regardless of which company made it. `omp` reports natively. Hermes reports through a plugin I wrote. The app does not need a special relationship with every agent vendor just to show whether its process is working or blocked.

That is why Herdr stuck for me. I argued the general version of this before, in [From Framework Fatigue to Ecosystem Fatigue](/blog/260410-from-framework-fatigue-to-ecosystem-fatigue) - the bill lands on you when the surface you depend on is a product instead of a protocol. tmux still gives me panes and persistence. The TUI made agents visible but kept them in a window. Core gives the terminals names and status without requiring that window; the desktop app and phone let me look in when I need to. Several agents can work together, and I can see where they are.

I stopped keeping every agent on screen. Now I check the herd when I need it.
